# Доказательная операционная модель Find Dream Job

Этот документ описывает пользовательскую evidence-модель схемы v6 и
совместимые операционные дополнения v7–v8. Технический контракт
CLI находится в [`JOB_SYSTEM.md`](../JOB_SYSTEM.md), а обязательные границы
действий — в [`AGENTS.md`](../AGENTS.md).

## Жизненный цикл и текущее действие

Жизненный цикл хранит подтверждённые факты, которые нельзя стереть новой
задачей:

- подтверждённый отклик;
- отказ;
- приглашение, назначение, завершение или отмена интервью;
- неявка кандидата или работодателя, если она подтверждена;
- предложение.

Текущее действие отвечает на другой вопрос: что нужно сделать сейчас. Например,
после подтверждённого отклика анкета работодателя может создать действие
`needs_input`. Отклик при этом остаётся подтверждённым. Очистка старого поля
этапа до `seen` также не отменяет отказ или другой доказанный факт.

Добавить текущее действие можно командой:

```bash
python3 scripts/jobctl.py set-current-action \
  --id 42 --action-state needs_input --bucket urgent \
  --due-date 2026-02-20 --priority 100 \
  --priority-reason "Нужен точный ответ на вопрос анкеты"
```

Факт жизненного цикла добавляется отдельно через
`record-lifecycle-event`. Подтверждённый отклик нельзя записать этой командой:
он появляется только после видимого подтверждения внешнего действия.

## Уровни доказательности интервью

Система различает:

1. `interview_invited` — получено приглашение;
2. `interview_scheduled` — назначено точное время;
3. `interview_completed` — интервью действительно состоялось;
4. `interview_cancelled` — интервью отменено;
5. `interview_no_show_candidate` — подтверждена неявка кандидата;
6. `interview_no_show_employer` — подтверждена неявка работодателя.

Для каждого события интервью обязателен положительный номер раунда. Для
`interview_scheduled` дополнительно обязательно назначенное время. Приглашение,
автоматическое письмо, просьба рекрутера выбрать время и запись в календаре не
считаются завершённым интервью.

Завершение подтверждается отдельным событием либо приложенным резюме интервью:

```bash
python3 scripts/jobctl.py attach-interview-summary \
  --id 42 --file private/interview_1.md --interview-no 1 \
  --date 2026-02-18 --confirms-completion \
  --completion-evidence-note "Проверено по итоговому резюме разговора"
```

Для такого подтверждения файл должен содержать не менее 80 непробельных знаков
и трёх содержательных строк. Без флага `--confirms-completion` файл остаётся
полезной заметкой, но не меняет показатель завершённых интервью.

Автоматические подтверждения работодателя хранятся отдельно от ответов людей и
не входят в показатель человеческих ответов.

## Карта исходов

Основная команда:

```bash
python3 scripts/jobctl.py outcome-scorecard --as-of 2026-02-28 --json
```

Единица анализа — одна каноническая вакансия и её самое раннее подтверждённое
событие отклика. Повторные строки и смена текущего действия не умножают и не
удаляют когорту.

Карта показывает:

- уникальные подтверждённые отклики;
- когорты, созревшие для оценки ответа человека через 14 дней;
- ответы людей и долю ответов;
- когорты, созревшие для оценки исходов интервью через 30 дней;
- приглашённые, назначенные и завершённые первые интервью;
- более поздние раунды и предложения;
- покрытие поиска контактов и проверенного пути к человеку;
- полноту структурированных полей.

Каждая доля содержит числитель и знаменатель. Если перенесённая историческая
запись не доказывает полноту истории, отсутствие исхода отображается как
`n/a`, а не как ноль. Для выборки меньше десяти откликов выводится отдельное
предупреждение.

Доступны разрезы по настроенной кампании, семейству ролей, потоку и каналу
источника, целевому работодателю, фактически отправленному резюме и варианту
сообщения. Источник отклика берётся из явной ссылки, а при её отсутствии — из
самого раннего касания до отклика; равные даты разрешаются по идентификатору
записи источника.

## Очередь WIP и сроки SLA

Очередь показывает ограниченный объём активной работы и отдельно считает
переполнение:

```bash
python3 scripts/jobctl.py wip-queue \
  --as-of 2026-02-28 --page 1 --page-size 100 --json
```

Стандартные корзины:

- срочный ответ работодателю или данные от пользователя;
- наступивший срок повторного обращения;
- углублённая проверка сильной возможности;
- исследование целевого работодателя;
- резерв вне активного лимита.

Лимит и срок SLA каждой корзины задаются в локальной конфигурации. Порядок
детерминирован: корзина, просрочка, глубина просрочки, приоритет, срок, время
действия и идентификатор вакансии. Возраст, срок, просрочка, причина приоритета
и превышение лимита видны в JSON, Markdown и панели.

Большая очередь разбивается на нумерованные страницы. Старые строки не
архивируются и не изменяются автоматически. Массовое изменение допустимо
только для точной однородной выборки после пробного запуска, аудита и явного
разрешения; встроенной возрастной очистки нет.

В v8 actionable WIP не включает последнее `action_state=none`, неактивную
корзину backlog и вакансии с terminal lifecycle (`rejected` или `offer`). Их
полная append-only история остаётся в `action_events` и `lifecycle_events`.
Очередь вычисляется один раз и затем разбивается на страницы.

Для daily run используйте `begin-daily-run`, передавайте
`--defer-render --run-lease <token>` каждой write-команде и завершайте одним
`finalize-daily-run`. Прерванная финализация не меняет предыдущую целостную
generation; её можно повторить с тем же token.

## Метки источников

`source_hits.source_stream` всегда хранит исходное значение без изменений.
Локальный раздел `[source_stream_aliases]` может явно связать всё исходное
значение с одной или несколькими нормализованными метками:

```toml
[source_stream_aliases]
"Campaign Alpha + Campaign Beta" = ["campaign_alpha", "campaign_beta"]
```

Знак «плюс» и другие разделители сами по себе никогда не разбираются. Один
исходный факт остаётся одной строкой, но получает две производные связи.
Изменение псевдонима применяется при пересборке и не уничтожает исходную
историю. Для первого касания используется первая явно настроенная метка.

Покрытие поиска, исходное обнаружение, первое касание и явно указанный источник
отклика остаются разными понятиями.

## Карантин и повторная обработка

В карантин попадают CAPTCHA, страницы без авторизации, ошибки доступа,
некорректные записи, опасные или неверные URL и записи без обязательных для
источника полей. Они сохраняют исходные данные, причину и контекст повтора, но
не участвуют в показателях вакансий, очереди, когортах и знаменателях качества
источников.

```bash
python3 scripts/jobctl.py quarantine-report --page 1 --json
python3 scripts/jobctl.py reprocess-quarantine \
  --id 17 --replacement-json tmp/corrected_record.json --json
```

Повторная обработка всегда относится к одному точному идентификатору. Для
исторических строк доступен только проверяемый пробный режим:

```bash
python3 scripts/jobctl.py classify-legacy-records --dry-run --json
```

Он ничего не изменяет и не присваивает неоднозначной истории причины задним
числом.

## Структурная и операционная проверка

`doctor --strict --json` проверяет структуру рабочей области и базы.
`operational-doctor --strict --json` отвечает на отдельный вопрос: можно ли
закрыть текущий ежедневный цикл.

```bash
python3 scripts/jobctl.py doctor --strict --json
python3 scripts/jobctl.py operational-doctor \
  --as-of 2026-02-28 --strict --json
```

Каждая операционная проверка имеет состояние `pass`, `warn` или `fail`. Общий
ответ содержит:

- `technical_health` — техническая исправность;
- `ready_for_daily_closeout` — готовность ежедневного закрытия.

Проверяются обязательные файлы, безопасные настройки внешних действий,
идентификаторы резюме, `quick_check`, внешние ключи, версия схемы, согласование
событий отклика, допустимость состояний, полнота полей, карантин, превышение WIP
и SLA, свежесть панели и отчётов, обязательное покрытие поиска, отдельный поток
персональных рекомендаций и включённые инкрементальные источники.

Отсутствующее или устаревшее обязательное покрытие делает
`ready_for_daily_closeout = false`, даже если техническая проверка зелёная.
Описание ошибки называет точное невыполненное условие.

## Целевые работодатели

Карточка целевого работодателя поддерживает лимит активного портфеля,
приоритет, состояние, периодичность и дату следующей проверки, свежесть
официального сайта и страницы вакансий, целевые кампании и семейства ролей,
доказательства владельца, спонсора и управления, путь к человеку и датированные
сигналы с уровнем уверенности.

Нужно сохранять четыре границы:

1. сигнал о работодателе;
2. соответствие конкретной вакансии;
3. балл кандидата относительно вакансии;
4. разрешение связаться с конкретным человеком.

Ни один сигнал работодателя автоматически не меняет балл вакансии и не даёт
разрешения на контакт.

## Явное разрешение внешнего действия

Баллы и пороги используются только для приоритета проверки. Они никогда не
разрешают отклик, сообщение, повторное обращение, изменение почты или
публикацию. Настройка `auto_apply` также не является разрешением конкретного
действия.

Внешнее действие хранит отдельные состояния:

- `drafted` — подготовлен черновик;
- `authorized` — получено разрешение на точное действие;
- `attempted` — попытка выполнена;
- `visibly_confirmed` — видимое подтверждение получено;
- `blocked` или `failed` — действие заблокировано или завершилось ошибкой.

Только `visibly_confirmed` создаёт факт подтверждённого отклика или отправки.
Повтор записи с той же внешней ссылкой идемпотентен.

## Версия политики и аудит пропусков

В каждый момент активна ровно одна версия политики отбора с датой вступления в
силу. Для отклонённых и низкоприоритетных вакансий сохраняются результаты
правил. Команда ниже строит воспроизводимую выборку и показывает частые правила,
которые требуют проверки:

```bash
python3 scripts/jobctl.py false-negative-audit \
  --as-of 2026-02-28 --sample-size 25 --seed review-2026-02 --json
```

## Переход на схему v6 и восстановление

Обычное обновление всегда создаёт резервную копию:

```bash
python3 scripts/jobctl.py migrate-schema --json
python3 scripts/jobctl.py rebuild --json
python3 scripts/jobctl.py doctor --strict --json
python3 scripts/jobctl.py stats
```

В схеме v6 поле `interviews` в выводе `stats` означает число вакансий с
доказанным завершённым первым интервью. Для прозрачности вывод также содержит
`interview_invitations`, `scheduled_interviews`, `completed_first_interviews`,
`later_interview_rounds` и совместимый счётчик текущего этапа
`interview_current_stage`. Переход вакансии к предложению или отказу больше не
стирает уже доказанное интервью из показателя.

Текущая схема v9 поддерживает перенос исходных версий v1–v8. Перенос сохраняет канонические вакансии,
псевдонимы, исходные метки источников, отклики, взаимодействия, карточки
работодателей и контрольные точки. Неизвестные исторические значения остаются
неизвестными. Повторный запуск миграции идемпотентен и не создаёт новую копию,
если схема уже актуальна.
После обновления не открывайте базу v9 старым Engine. Для отката сначала
восстановите автоматическую резервную копию, затем используйте прежнюю
совместимую версию кода; разрушающей обратной миграции нет.

Имя резервной копии имеет вид
`job_search.sqlite.bak-schema-v<версия>-<дата-время>`.

Если проверка после обновления не прошла:

1. остановите процессы, которые пишут в базу;
2. сохраните текущий неудачный файл отдельно для диагностики;
3. выберите резервную копию, созданную этим запуском;
4. восстановите её по настроенному пути `data/job_search.sqlite`;
5. запустите предыдущую совместимую версию Engine;
6. выполните `PRAGMA quick_check`, `PRAGMA foreign_key_check` и
   `doctor --strict --json`;
7. не запускайте разрушающую обратную миграцию.

Резервная копия содержит приватные данные и должна храниться с теми же мерами
защиты, что и основная база.
